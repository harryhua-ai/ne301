# Issue #80: Signed App UI sidecar offline feasibility

Date: 2026-10-14

Scope: offline fixture, local mock Host/Publisher, local HTTP browser experiments, and source-based storage/RAM estimates. This document is evidence for architecture review; it is not production implementation authorization and does not mark the feature DONE.

## Conclusion

Overall feasibility on the target NE301 board is **UNKNOWN**. A reproducible desktop fixture demonstrates that the four historical people-counting UI components can be built and used across a separate browser origin with a narrow typed bridge. An offline test model demonstrates a signature and asset-integrity join to the native v3 identity tuple, while all 61 existing v3 admission tests continue to pass with a separate temporary test anchor. The reviewed Host code has no sidecar mount, serving, or rollback path, and neither target-device free LittleFS bytes nor target loading RAM were measured.

Current transport security is **NO for HTTP**: an independent origin and a valid signature do not protect HTTP responses from an on-path party that can replace the delivered page before the browser runs it. The fixture deliberately uses local HTTP only. TLS can protect transport confidentiality, integrity, and server authentication, while signed manifest verification remains a separate authorization check. The reviewed `web_config.h` currently sets `IS_HTTPS` to `0`; no device was contacted. See [MDN Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) and [MDN TLS](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Transport_Layer_Security).

## Reproduction and evidence

Run from the repository root on a machine with Node.js 22, npm 10, a C compiler, and installed Google Chrome:

```sh
cd tests/app_ui_sidecar
npm ci
npm test
```

`npm test` builds from the pinned historical source commit, runs the offline binding negatives, compiles and runs the unchanged native v3 test source with fresh temporary test keys, then launches installed Chrome in headed mode for browser automation. The local mock servers bind only to loopback and use ephemeral ports. No device, production certificate, MQTT, webhook, or external service is involved. The build output and temporary keys live outside the repository.

Evidence generated by that command:

- `tests/app_ui_sidecar/evidence/source-closure.json` — source commit, SHA-256 for every copied historical file, fixture adapters, and pinned fixture dependencies.
- `tests/app_ui_sidecar/evidence/fixture-metrics.json` — compiled file count and signed bundle size measurements.
- `tests/app_ui_sidecar/evidence/test-all.log` — build, binding, native v3, and browser test output.
- `tests/app_ui_sidecar/evidence/native-v3-existing-harness.txt` — unchanged v3 test output (`total=61 fail=0`) from a temporary independent test anchor.
- `tests/app_ui_sidecar/evidence/browser-automation.json` — Chrome version, loopback origins, observed response headers, cache probe, desktop sidecar JavaScript heap sample, capability audit, and bundle measurements.
- `tests/app_ui_sidecar/evidence/people-counting-sidecar.png` — real Chrome screenshot after the UI and interaction probes.

The browser run can also be repeated alone with `npm run test:browser`. `playwright-core` uses the installed branded Chrome channel; see the [official Playwright browser documentation](https://playwright.dev/docs/browsers).

## AC1 — historical UI fixture

**Result: YES for the reproducible desktop fixture.** The Vite entry renders the actual `index.tsx`, `VideoPreview.tsx`, `StatsPanel.tsx`, and `ConfigPanel.tsx` from commit `6fb5dd798ef623316971816475be2208d9fbe018`; no replacement static page is used. The copied dependency closure includes the historical Card, Button, Label, Input, Switch, Android switch/detector, dialog, SVG icon, `lib/utils.ts`, people-counting/device API wrappers, CSS, and English locale. Their source hashes are in `source-closure.json`.

Fixture inheritance and substitutions:

- Preact hooks and the historical components are retained. The fixture build aliases React imports to `preact/compat` and uses the pinned Radix, Lucide, Tailwind, and Preact packages listed in `source-closure.json`.
- The original API wrappers remain in the build. Their request transport is mapped to the typed local bridge; configuration, statistics, backlog, preview start, and preview stop do not reach a device.
- Lingui, Sonner, websocket URL construction, and `H264Player` are replaced by named local adapters. The `VideoPreview` component, SVG line overlay, controls, and save flow remain the historical source. The video adapter draws a deterministic local canvas stream and opens a local websocket; it is not an H.264 decoder or device video stream.

Pinned build measurement: **5 UI assets / 176,168 asset bytes; 7 signed bundle files / 176,888 expanded bytes; 55,016-byte deterministic `tar` + gzip archive; 231,904-byte archive-plus-expanded staging proxy.** The seven files are five Vite output assets plus `manifest.json` and a 64-byte signature. The bundle manifest is 656 bytes. These sizes exclude filesystem allocation units, directory/inode overhead, and the NE301 package container; they are not the final device package size. The test-only Ed25519 key is deterministically derived for stable measurement and is not a usable production trust root.

The Chrome probe confirms the actual configuration controls, statistics values, video panel, line edit/save interaction, HTML video playback from a canvas stream, `MediaSource` codec capability, WebSocket establishment, and a module Worker. It does **not** establish that the historical H.264/MSE player works on the target browser or board, because that player was intentionally replaced by the local video adapter.

## AC2 — test-only signed binding semantics

**Result: YES for the offline semantic model; production trust remains UNKNOWN.** `binding.mjs` verifies a separate `sidecar-probe-v1` signature domain, test-root key SHA-256, strict asset manifest, exact byte size and SHA-256 for every asset, and a binding to all trusted native fields: `packageSha256`, `publisherId`, `appId`, and `keySha256`. The mock Host refuses mounting when that tuple no longer matches the currently trusted native record.

The ten binding tests cover accepted test-root binding; altered asset bytes, manifest, or signature; unlisted assets; absolute, traversal, encoded, and backslash paths; duplicate asset path and sidecar name; cross-package binding; old neapp-v3 signature-domain rejection; unknown UI root; stale binding on native upgrade; and stale binding after native uninstall. They are deliberately experimental encoding, not a frozen wire format. The original `tests/app_admission/test_app_admission_v3.c` and native admission implementation are not changed. The harness supplies fresh keys and a temporary test anchor without reading or replacing any repository, production, or device trust anchor; result: **61/61 existing v3 cases pass**.

## AC3 — desktop browser isolation and capability bridge

**Result: YES for the tested Chrome/loopback HTTP configuration.** Host, sidecar v1, sidecar v2, and attacker pages use distinct ephemeral ports. Scheme, host, and port form the browser origin, so different ports on loopback are cross-origin. The iframe has `sandbox="allow-scripts allow-same-origin"`, no top-navigation permission, and the sidecar response uses a host-specific `frame-ancestors` CSP. `allow-same-origin` is safe in this probe only because the sidecar is on a distinct origin; do not serve it from the Host origin. MDN warns against combining `allow-scripts` and `allow-same-origin` when the embedded page shares its parent origin. See [MDN origin rules](https://developer.mozilla.org/en-US/docs/Glossary/Origin), [iframe sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe), and [CSP frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/Clickjacking).

The narrow bridge accepts only config read/write, stats read, backlog read, stats reset, and video open/close. It checks frame source, exact origin, one-use generation nonce, capability name, and field types/ranges. The browser automation rejects Host DOM/cookie reads, an unlisted native capability, an invalid configuration value, forged Host and sibling-frame messages, correct frame source with an origin mismatch, a stale nonce after iframe rebind, stale same-origin service-worker code despite `no-store`, top-level navigation, and third-party embedding under CSP. It also checks that a new origin loads the new build and that bridge access still functions after rebinding.

The same-origin service worker is an explicit counterexample: it continues returning its cached v1 document and label after the server changes to v2 and sends `Cache-Control: no-store`. The new origin has no old service-worker registration and returns v2. A production design therefore needs explicit version/cache invalidation and nonce rotation across unload, upgrade, rollback, and uninstall.

The fixture uses HTTP and WS (`ws://`) on loopback so transport protection is **NO** in this experiment. Origin checks constrain browser document access; they do not authenticate an HTTP server or prevent a network intermediary from replacing the document and its scripts. HTTPS/TLS improves transport confidentiality, integrity, and peer authentication but does not replace the signed asset manifest, native tuple binding, or capability checks. A production certificate and its provisioning path were not tested.

## AC4 — 32 MiB LittleFS estimate and unknowns

**Result: budget model completed; target capacity and runtime feasibility UNKNOWN.** `Custom/Common/Inc/mem_map.h` defines LittleFS as 32 MiB for the 64 MiB flash layout and 96 MiB for the 128 MiB layout. The 32 MiB value is partition capacity, not currently free storage. Relevant source facts are:

- `APP_INSTALL_PKG_DIR` is `/apps/pkg`; the current v3 max package length is 2,097,432 bytes (`app_admission.h`).
- The native installer stores 296-byte committed and 312-byte pending metadata records in NVS; they are not LittleFS bytes. It requires `free_bytes >= 2 * incoming_package_length` before native install and only removes an old package after the replacement record commits (`app_installer.h`, `app_installer.c`).
- The fixed WEB partition is 1 MiB. `web_assets.h` reports 88,592 bytes for the current static Web bundle; `web_assets.c` copies the asset blob and separately allocates its file index in RAM. That is separate from LittleFS and is not the measured sidecar bundle.
- The proposed active/pending sidecar metadata is not implemented. For a lower-bound worksheet only, use two measured manifest/signature pairs: `2 * (656 + 64) = 1,440` bytes. Filesystem allocation and transaction metadata are additional unknowns.

| Sidecar replacement state | Bytes |
| --- | ---: |
| Existing native v3 package, conservatively at max length | 2,097,432 |
| Old expanded UI retained for rollback | 176,888 |
| New expanded UI | 176,888 |
| Staged compressed UI archive | 55,016 |
| Two measured manifest/signature metadata pairs | 1,440 |
| **Modelled subtotal before LittleFS overhead and other data** | **2,507,664** |
| 32 MiB partition arithmetic remainder before overhead/other data | 31,046,768 |

If a maximum-size native package update overlaps the sidecar replacement, add another 2,097,432 bytes for the new native package staging, yielding a **4,605,096-byte subtotal** before overhead and other LittleFS contents. The existing native installer’s two-times free-space precheck is a source fact for native package installation; it is not a sidecar guarantee and does not expose the current device free-byte count.

Peak target RAM is **UNKNOWN**. At final capture, desktop Chrome reported 12,289,585 bytes used JS heap and 15,973,529 bytes total JS heap for the page context; this is a browser-side sample, not an isolated device measurement or target budget. The board’s server heap, process memory, stack, websocket buffers, filesystem cache, and fragmentation were not measured. A conservative server that loads all expanded sidecar assets plus metadata would need at least the 176,888-byte bundle payload, plus file table and request buffers; none of those target allocations were measured. The existing static Web asset loader already copies its asset blob and index into RAM.

Reproducible local sizing steps are `npm ci && npm run build:fixture` and inspection of `evidence/fixture-metrics.json`. A later target-specific measurement, under separate authorization, must record the board SKU/flash map, current LittleFS `free_bytes`, installed native `package_len`, all other LittleFS occupants, actual on-disk archive and expanded asset allocation, sidecar metadata allocation, and peak server RAM. It should interrupt power at each future staged/verified/pending/active transition and verify old-UI rollback and orphan cleanup. No target measurement is represented as PASS here.

## Counterexamples and minimum next behavior contract

Counterexamples observed: HTTP cannot provide TLS transport protections; `no-store` does not invalidate an already controlling service worker; old sidecar bindings become unmountable after native package identity changes; and the current Host has no sidecar mount/serve/rollback path in the reviewed implementation. The canvas video adapter is also not evidence of target H.264 decoding.

The next architecture contract should specify, before implementation:

1. The exact signed identity tuple `(native package SHA-256, publisher ID, app ID, publisher-key SHA-256)`, independent sidecar signature domain and trust lifecycle, and the rule that v3 admission remains unchanged.
2. Canonical manifest fields, exact normalized paths, duplicate/case-collision behavior, byte sizes and hashes, no unlisted files, and the binding between the verified manifest and the selected Host origin.
3. The sandbox/CSP/origin policy and typed capability schemas, deny-by-default behavior, per-request limits, a total file/byte quota tied to measured free space, nonce rotation, and cache invalidation after upgrade, rollback, unload, or uninstall.
4. A durable staged → verified → pending → active state machine, power-loss recovery, rollback retention, orphan cleanup, and fail-closed handling when free space is unknown.
5. A transport plan with authenticated HTTPS and separately verified signed assets; a target-specific free-space reserve, RAM ceiling, and browser/video/worker support matrix.

No production loader, API permission system, upgrade path, trust root, device storage, or firmware behavior is implemented or authorized by this investigation.
